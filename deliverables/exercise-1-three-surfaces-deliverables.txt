Summary:

Backend — where quiz data is loaded
- backend/src/quizService.js defines loadQuiz(), which reads backend/data/quiz.json
  from disk with readFileSync, parses JSON, and caches the result in cachedQuiz.
- getQuizForClient() returns id, title, description, and questions without
  correctOptionId so clients cannot cheat from the GET payload.
- gradeQuiz() loads the same cached quiz and compares submitted optionId values
  to correctOptionId inside backend/data/quiz.json (via the in-memory object).
- backend/src/server.js wires HTTP: GET /api/quiz calls getQuizForClient(); POST
  /api/quiz/submit validates the body and calls gradeQuiz(answers).

Frontend — how the API is reached in development
- frontend/src/api.js uses relative fetch("/api/quiz") and fetch("/api/quiz/submit",
  { method: "POST", ... }). The browser talks to the Vite dev server on port 5173.
- frontend/vite.config.js configures server.proxy so paths starting with /api are
  forwarded to http://localhost:4000 (the Express backend). That avoids configuring
  CORS on the client for local dev.

Environment variables
- Grep shows only backend/src/server.js uses process.env: PORT with a default of
  4000 (process.env.PORT ?? 4000).
- There is no .env file in the project; frontend port 5173 and the proxy target
  are hardcoded in vite.config.js. README.md documents the local URLs.

DELIVERABLE 5 — WRITTEN COMPARISON (5–10 SENTENCES)
================================================================================

Cursor Tab felt like the fastest surface for micro-completion inside a single
function: in quizService.js it proposed the next lines without a prompt, which
is ideal when the pattern is already obvious (cache, parse, return). The
suggestion quality depends on immediate context; I still reviewed before
accepting because Tab optimizes for flow, not for explaining tradeoffs.

Inline Edit (Cmd+K) was the most controlled surface for a localized change. By
selecting only the POST /api/quiz/submit handler in server.js and giving a
specific validation instruction, I got a tight red/green diff that stayed inside
the selection scope instead of touching unrelated files. I would use Inline Edit
for refactors, renames, and endpoint-level validation where I want deterministic,
reviewable edits.

The Agent sidepane (Cmd+I) behaved differently: it prioritized exploration and
cross-file reasoning—connecting quizService.js, server.js, api.js, and
vite.config.js—rather than silently patching code. That made it better for
onboarding questions (“where is config loaded?”, “how does dev proxy work?”)
before I choose Tab or Inline Edit to implement.

Overall I would use Tab to write faster inside known patterns, Inline Edit for
surgical edits with an explicit instruction and diff, and Agent when I need
multi-file context or I am planning a change across frontend and backend. In
cursor-app, Tab and Inline Edit are enough for small features; Agent adds the
most value when the question spans both packages and documentation.
